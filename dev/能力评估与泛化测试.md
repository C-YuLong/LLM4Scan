# 能力评估与泛化测试（2026-10-01）

## 结论

已有公开案例累计通过不能证明隐藏测试能力。本轮以一个原创小电路、两个任务模式
及四组中文改写检查泛化，发现一个真实系统误拒问题、四类需求漏检和根因重复诊断。
修复了系统误拒，其余缺口保留为后续能力目标；没有为测试改写四组特例正则。

## 已定位不足

### 1. 验收器自身会因名称变化误拒正确结果（已修）

`submission/acceptance.py` 在完整分区表不含字面单词 `partition` 时，读入第一行后，
用不断变化的 `req["partitions"]` 判断是否跳过后续行。本案例使用正常的
`ingress` / `egress` 名称，因此丢掉 egress，错误触发 `task_no_extra_partition_chains`。

修复为在遍历完整表之前记录是否已解析了分拆表，避免第一行修改循环控制条件。
不依赖新案例名、链数或分区名。新增本案例表格回归，连同已有分拆表回归共两项通过。
Task 1 原 R1 的独立审计确认：3 条长度 4 的链、12 个实例各一次、时钟域归属正确、DRC 0。
修复后 Task 2 的交付另经相同语义检查及证据引用/文件一致性检查通过。

### 2. 需求识别对中文表达敏感（未修）

例如“共 3 条链”能识别，“扫描链总数必须等于 3”不能；“DRC 检查无违例”能识别，
“DRC 违例数必须为 0”不能。这是确定性验收层的缺口，不是本轮证明模型不会理解这些话。
部分未提取的要求不会产生对应失败项；因此 `accepted=true` 不能理解为所有自然语言要求均已证明。

建议下一阶段复用现有模型生成计划中的 requirement mapping：每条明确要求带原文引用，
把可测量约束转换成类型化字段，然后由现有报告检查器执行。必须明确标记未覆盖的要求；
保留原文/程序约束交叉检查，不能让生成脚本的模型随意删除或放宽自己的验收标准。
先只覆盖已有检查器支持的链数/链长/信号/分区/Wrapper，不扩展成通用自然语言框架。
开发样本和验收样本分开，不能以这四组改写全部变绿作为泛化成功标准。

### 3. 根因粒度还不稳定（未修）

开发侧在执行前固定了两个注入操作：tick_b → tick_wrong；ingress 链数 2 → 1。
两次 Task 2 都诊断出三个条目：不存在的 tick_wrong、遗漏 tick_b、错误链数。
两个注入操作都被找到，但同一时钟拼写替换被拆为两个根因。

现有 `sanitize_diagnoses()` 只按命令和根因文本的完全相同组合去重，无法识别这种因果重复。
建议以修复 diff、被违反的要求和故障因果关系联合复核：同一替换修复导致的多个症状
是否属于一个根因。不能只按共同端口/同一行强行合并，单行也可能含多个独立配置错误。
本实验的根因口径是预先定义的开发 oracle，不宣称等同于官方评分口径。

### 4. 结构/功能证明与大设计上下文仍有空白（代码审查，不是本轮新增实测）

- `design_outline()` 对超过 2000 个层级对象的设计裁剪上下文，并依赖部分模块命名识别控制结构；
  隐藏的深层控制逻辑可能不进入模型上下文。适合后续做中性模块名、深层门控的定向案例。
- 预处理的独立结构审计仍主要在开发侧；普通运行时输出存在性不证明排除域未被修改。
- CTL/链报告一致不证明网表实际扫描连通性或功能等价。本轮未做 LEC/EQY。
- 截断日志/报告可能遗漏根因证据；本轮未重新测量大设计性能，不虚构改善幅度。

## 开源设计候选（已核对仓库，不是已跑通）

2026-10-01 读取 GitHub 仓库元数据；另读 SERV、verilog-i2c 的 README。
未下载第三方源码进本仓库，也未将其综合/执行 Scan。

| 候选 | 查到的许可证/状态 | 能补的覆盖与成本 |
|---|---|---|
| [SERV](https://github.com/olofk/serv) | ISC；README 提供 FuseSoC 流程 | 小型串行 RISC-V 核；适合换设计验证，不把芯片名作为能力点。优先级最高 |
| [verilog-i2c](https://github.com/alexforencich/verilog-i2c) | MIT；README 声明已弃用，后继为 taxi | 可固定旧提交选择外围模块，补非 CPU 逻辑；不能称其仍积极维护，也不能把许可结论转移到后继项目 |
| [Ibex](https://github.com/lowRISC/ibex) | Apache-2.0（仓库元数据） | 更复杂核；需进一步核对构建/依赖和各文件许可，当前不优先 |

这些是 RTL 项目，不能直接当门级 Scan 输入。引入时必须固定提交、选择不含未建模宏的顶层，
先完成综合和目标 Liberty 映射，检查可扫描 FF 映射、复位、时钟、latch/memory 和黑盒处理，
再给智能体做插链；否则测出的可能只是前处理失败。保持许可证和来源说明。

## 推荐下一阶段

1. 先完成“需求覆盖可见、约束类型化”的最小实现，用未参与开发的中文表达做验收。
