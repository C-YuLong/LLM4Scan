## 本轮主要改变

1. **不再用少扫寄存器换通过。** 修复前冻结任务允许的排除范围，检查完整寄存器报告。曾被旧检查误放行的“额外排除 783,928 个 RAM FF”现会失败；d39、d44 大例均真实扫描 799,031 个目标 FF，只排除任务允许的 94 个 TAP FF。
2. **修复不能丢功能。** 发现并拦住带数据使能 FF 的错误映射和工具导出常量连接失真。实际模型已能对 UART、SERV 和层级迁移题做等价工作副本改写。真实 EQY 比较原始输入与最终采用的 Pre-scan，不固定输入；错误连接负例未被证明，Scan 不启动。证明不是对所有 Post-scan 的通用功能认证。
3. **诊断可追溯。** 原始问题绑定真实源行，修复依据绑定真实产物行；独立参数、独立复位域不应合并。已补强确有证据的遗漏检查，并实测拦住“允许忽略就必须忽略”的误报。单条引用存在不等于其因果解释正确。
4. **降低无效开销。** 同一工具产物可以做诊断-only 复核；不重复运行不变脚本。EQY 中间文件移到容器原生临时目录，实际同配方证明从 381 秒降至 64 秒，完整证据仍归档。知识检索保留完整相关条目及可信度，不再整篇历史塞入上下文。

收尾时又修复完整寄存器报告检查的正则回溯：约 235 MB 合法报告的检查阶段实测 0.402 秒；159 MB 旧错误报告仍识别并拒绝全部 783,928 个越界 FF。两项既有检查及真实完整报告重审通过，没有重新调用模型或 Scan。该项是下面 d49 的定向验证，不能拿它推算全部运行时间。

## 仍未解决

- **诊断因果误报。** 部分运行仍将正边沿 FF 当作时钟 `off_state=0` 的必然依据。已有单变量工具反事实反驳该题指控；提示词和字段排序不足以保证模型不再犯错，不能说诊断已满分。
- **额外控制声明的开销。** d48 大例 R2/R3/R4 因多余 JTAG 声明依次残留 2/4/1 条 DFTR8，R5 自动撤回多余时钟和复位后通过，仅余四条允许的 DFTR10。最终成功但花费约 36 分钟，不能称高效稳定；诊断条目数不代表满分。
- **诊断检查与交付对应。** T2/C3 后续复查发现：诊断已明确写出缺少 `rpt_scan_element -type all`，却因为 `defective_parameter=-type` 被检查程序误判为漏项；之前“模型遗漏”的归因有误。T1/C6 的需求映射引用 `if {[llength $indices] >= 10]`，实际脚本为 `if {[llength $indices] >= 10} {`，是引用抄写错误，不是工具语法错误。这两处在十小时截止时均未修复；后续修复与新结果单独记入完整迭代记录。
- **短时限波动。** 引用或需求纠正会耗掉 140 秒内部预算；通过一次不等于稳定通过。
- **两道参考待定题。** H05 的两级状态控制初始化尚无合法完整参考；512 FF 复用层级题的旧成功使用了不满足同波形前提的时钟关联，已撤回资格。原输入、失败和撤回记录保留，没有改题刷通过。
- **正式环境未重测。** 用户未授权其他 Key，当前平台又不允许 Luna；没有通过换 URL、旧 ZIP 或其他凭据绕过限制。

## 复现与协作

在本地已有官方基础镜像、输入及合法 License，并已配置获授权的 gproxy 后：

```powershell
# 使用冻结代码顺序运行公开题；必须选从未使用过的结果前缀。
python -X utf8 dev/run_stage.py --image localhost/scanscan:iter10h-d48 --output-prefix reproduce_d48_new
```

不指定 `--image` 会挂载当前源码；不能用该模式宣称测的是某个冻结镜像。逐例结果、完整日志、修改记录、最终产物和独立验收在 `dev/results/<前缀>*`；旧结果不会覆盖。本机大网表必须串行，详见 [协作说明](../CONTRIBUTING.md)。

本轮不推 Git、不提交平台、不打包密钥。代码、开发工具和带可信度的 `knowledge/` 可协作；官方资料、输入、模型响应、镜像和产物留在本地忽略目录。

用量以各汇总的 `token_usage` 为准：包含已返回响应，不等于账单；未返回或中断请求可能缺失。不能拿 DeepSeek 的单价给 Luna 直接计费，也不把未知缓存数记为零。
