## 核验器修复与重测

针对前述实际失败修改现有流程：

- `result.finalize` 在处理结论前汇总无效原文引用，返回具体字段路径和合法行号；direct 在原有调用额度内纠正最终参数。输入或产物发生变化仍中止核验，不作为可纠正的引用错误。
- direct 提前一轮要求提交，为最终参数纠错保留一次调用；普通证据查询的参数纠错仍可继续。默认最多 8 次调用、120 秒核验预算及证据标准保持不变。
- 共享工具说明明确发布时序：`final.dofile` 对应候选脚本，`decision_log.json` 由 runner 在接受后完成；通过已有 `check_delivery` 核对候选就绪状态。最终发布检查保持原样。
- guided worker 直接以分配的要求建立初始问题，省去重复的 `set_question` 模型调用；规划说明要求合并可由同一比较建立的义务，保留全部例外；最终状态优先比较原输入与最终候选。

### 遇到的问题与修改

- 直接使用原有推理设置时，冻结候选的 direct 复核第二次调用以 `response.incomplete` 结束：3,000 个输出 token 全用于推理，未返回工具调用。启动器现在为 Flash 设置 `LLM_REASONING_EFFORT=none`；submission 使用该显式值，未设置时沿用原策略。Ourmethod 复核使用已有 `config.direct_agent.toml` 的 none 设置。未扩大 120 秒、8 次模型、24 次工具、每次 3,000 输出 token 的核验预算。
- Flash 部分 Responses 返回虽然声明严格 JSON Schema，实际内容仍含 Markdown 代码围栏及重复转义。将 Chat 已有的 JSON/字段校验与 `ModelResponseError` 原文保存复用于 Responses；不剥离围栏、猜测修复或执行无效字符串。两种协议的指令均明确 schema、无围栏和仅一次 JSON 转义。既有要求提取纠错因此能收到 Responses 格式错误及用量，调用额度不变。
- T2/C1 提取时曾擅自将题目中的 `dfxtp_1` 扩展成完整库名，连续两次被原校验拒绝。现有提示明确 target/value 必须逐字出现在引文中，库名前缀由现有 Liberty 解析处理。未放宽约束验证。
