# 控制拓扑与在线验收阶段

## 结果（2026-10-01）

本阶段补充六个不同控制拓扑的合成案例，用真实 Luna + Scan 暴露系统缺口，再只复测失败例。初始冻结批次 **3/6**；三个失败例定向修复后，跨版本已有 **6/6** 通过记录。最终所选结果的四个注入根因全部命中，误报/重复与漏报均为零；H06 无故障对照保持 R1、零诊断、零修改。

不是同一最终版本首次六连过，也不是官方成绩或六个独立工业 IP。最新 `capability17` 只运行了 H07；本阶段没有重跑公开 11 例或 Scan32 全集。额外探索例 H05 的参考流程尚未跑通，不计入六例模型成绩，仍是明确的未完成项。

## 实际修复了什么

### 1. 由实际连接提取控制上下文

新 `submission/control_context.py` 从输入 Liberty 的 FF/latch 控制引脚出发，沿网表组合逻辑、assign 和模块端口绑定提取上游片段，不依赖实例名包含 clk/clock。保留模块声明、源文件行号，以及实际 Liberty 输出函数与状态函数，供 Task 1 规划、Task 2 诊断和核验共同使用。

这解决了合并大文件中控制片段不被提供、跨模块同名信号混淆、仅凭 mux 名字猜选择极性的问题。遇到 FF 状态边界明确停止，不声称跨 FF 数据路径已经完成可控性证明。控制追踪有源语句与字符预算，完整输入仍由 Scan 工具读取；不是完整 Verilog elaboration 或形式验证。本轮未重新验证该解析在百万 FF 上的耗时和内存。

### 2. 将真实成员一致性接入在线验收

`submission/acceptance.py` 新增链单元唯一性、序号连续性、链长和 CTL 成员顺序/数量检查。对 CTL 黑盒，依据真实 `inferred_from_ctl` 段报告的实例范围和位数处理“不出现物理 cell-report 行”的合法情况，不按设计名字豁免。

失败详情进入既有修复流程。以保留的显式 Segment 和公开 C3 Wrapper/CTL 产物做只读兼容检查，并用重复成员、CTL 重排验证拒绝能力。这些检查没有证明输入所有应扫描 FF 都被正确分类；开发侧的网表功能引脚、控制连接和逐个扫描串行线审计仍未全部搬进运行时。

### 3. 默认分区是独立约束

H03 初始候选满足四条链和链长，却新建 `data_partition`，违反任务要求的默认分区。新增 `chain_partition` 约束并与已有分区契约核对，在线验收直接检查实际链所在分区，不以链数正确替代分区正确。

`repair15_scope` 最终通过。不过该次 R1 被拒绝的实际原因是额外门控配置导致 `Nothing matched`，当时默认分区已经正确；不能把这次 R1→R2 写成“分区检查触发修复”的实测证据。错误分区拒绝分支由定向单元检查验证。

### 4. 不沿用未经证实的内部时钟关联

H04 初始把 selector 常量错误诊断为“缺少内部时钟关联”；后续即使改正常量，仍保留多余 `associated_internal_clocks`，残留 DFTR8，12 轮后超时。独立参考脚本无需该关联即可通过。

补充实际 Liberty 函数和模块作用域，并在现有命令指导中要求比较原脚本与候选新增配置、重新审视无证据的关联。定向运行正确定位 selector=1 应改为 0，R2 达到 DRC 0、896 个数据 FF 全覆盖、四条默认分区链，无需手工替换候选脚本。

### 5. 阻止“修好了但没报告”的显式信号缺陷

H07 初始脚本修正了复位极性与模式常量，但只报告模式常量，仍应判失败。`repair_task.py` 新增范围有限的诊断覆盖检查：原脚本单行、单端口、显式 0/1 的 `set_scan_signal`，同时具有冻结任务约束和原始失败的信号值验收，才要求诊断引用对应原始命令。

遗漏时，在执行修复 Scan 前最多要求模型纠正一次，不扩展总 deadline、不由程序编造根因；再次遗漏则不接受。省略默认值、任意复杂 Tcl 或单纯 DRC 症状不自动转换成新问题。

H07 最新实测中，第一次计划有复位诊断，但任务引用不是精确原文，被原有证据过滤器拒绝；新增检查发现过滤后的漏项，要求模型修订一次，最终保留两项有准确引用的诊断。`model_plan.json` 保存两次计划、过滤结果、缺口和模型用量。实际 R1 DRC 含 clear_h 的 DFTR8，最终 R2 DRC 为零；没有伪称被掩盖的症状都在原始运行中出现。

以上实现只读取任务、实际网表/库和工具输出，不读取测试 oracle，不按案例名分支。

## 评分器修正与未完成探索

工具合法消除 `assign gated = e4`、`assign bridge = e2` 后，输出引脚直接使用等价信号。原开发侧评分器按字面比对，误报 H03/H06 功能连接变化。现按冻结原输入和实际输出的简单 assign 等价关系比较；FF 类型、扫描使能、串行线、分区和根因标准未降低。

已对旧产物重评分，没有再次调用模型或 Scan。H06 恢复通过；H03 的功能别名误报消除后仍因真实错误分区失败。原始评分保存为 `runs/frozen14/score_initial.json`，现行评分为同目录 `score.json`，原运行和输入均未改动。按修正后的评分器，冻结批次综合通过 3/6，产物通过 4/6，根因 TP=2、FP=1、FN=2。

H05_state_pipeline（1,024 个数据 FF 加两个排除的控制 FF）尝试真正的两级 FF 控制传播。初稿以 scan-enable 驱动，后在正式模型运行前改为独立 mode_pin=1，初始化四拍；两次参考流程仍有 1,024 个 DFTR9。尚未证明它可由现有参考配置正确完成，也没有证明它不可解。没有通过忽略 DRC、改变答案或排除数据 FF 把它计绿。

原预检输入与失败日志分别保存在 `benchmarks/control6_preflight/`、`benchmarks/control6_preflight2/`。H05 在主目录保留为额外探索例，六例正式模型组使用 H07 补充，排除 H05 的事实明确保留。

## 本地文件与复现

生成器和独立评分入口：`dev/control_stage.py`，复用 `dev/challenge_suite.py`。本地资产在 [benchmarks/control6](../benchmarks/control6/README.md)，由 Git 忽略：

- `cases/<case>/input/`：任务、限制、网表、Liberty 和 Task 2 原始脚本；模型只挂载此目录和自己的输出目录。
- 同级 `oracle.json`、`correct.dofile`：隔离的预期结果和参考脚本，不挂载给模型。
- `qualification/`：明确标记为参考工具执行，不计模型通过率。
- `runs/<batch>/<case>/`：逐轮脚本、日志、报告、网表、验收、诊断及最终交付。
- `runs/<batch>/score.json`：该批次实际镜像、逐例耗时和分项成绩，不隐去失败。

批次成绩：[frozen14](../benchmarks/control6/runs/frozen14/score.json)、[repair15_scope](../benchmarks/control6/runs/repair15_scope/score.json)、[repair16_mux](../benchmarks/control6/runs/repair16_mux/score.json)、[repair17_diagnosis](../benchmarks/control6/runs/repair17_diagnosis/score.json)。这些是本机链接，Git 仓库不包含运行资产。

新环境在准备官方基础镜像、库和本地模型配置后，可生成案例并运行；已有标准案例目录不要再次 prepare，运行批次名也必须是新的：

```powershell
python -X utf8 dev/control_stage.py prepare
python -X utf8 dev/control_stage.py run --batch experiment01 --image localhost/scanscan:capability17
```

只定向执行一个案例或重评分已有批次：

```powershell
python -X utf8 dev/control_stage.py run --batch experiment02 --cases H07_reset_mode --image localhost/scanscan:capability17
python -X utf8 dev/control_stage.py score --batch experiment02 --cases H07_reset_mode
```

`score` 不调用模型/Scan，但会更新批次评分文件；要保留旧评分时先复制备份。单例批次重评分须传相同的 `--cases`。默认六例不包括 H05，显式 `--cases H05_state_pipeline` 才会选择该探索例。

## 下一步优先级

1. 先确认 H05 的工具语义与可行参考，解决真正的跨状态控制传播，不能继续仅加组合级数后宣称时序深度提升。
2. 在少量未参与开发的开源工业模块上冻结版本评估，并包含新控制提取的大网表成本；目前全过记录主要证明这些合成能力点已跑通，不证明泛化。
3. 继续收紧诊断对象路径精度，并按实际失败需要接入输入 FF 覆盖/网表连接验收；不把 CTL 与报告一致当成完整 LEC。
