# Scan32 本地能力挑战

用户要求：约 32 个案例，规模覆盖公开例上下、包含高难组合，使用真实系统完成而非只生成输入。

## 实测交付结果（2026-10-01）

32/32 个案例均已有真实 Luna + Scan 全流程通过记录，并通过本地独立产物验收。Task 1 为 15/15，Task 2 为 17/17；29 个注入根因全部命中，误报/重复报告 0、漏报 0。两例无故障对照 C14、C29 都以原始 R1 通过，零诊断、零修改。

这是一轮**跨版本开发、定向修复后的成绩**，不是同一冻结版本首次 32 连过。最新 capability12 实测了 C25～C32，8/8 通过；为避免重复消耗，没有将已通过的其余 24 例再全部重跑。

| 项目 | 实测结果 |
|---|---|
| 最小案例 C01 | 8 FF，1 轮，55.98 秒 |
| 高难层级案例 C31 | 786,432 FF，2 轮，767.61 秒；768 条内部链，最大长度 1,024，32 个排除 FF 保持不变 |
| 最大复合案例 C32 | 1,200,000 FF，2 轮，829.94 秒；1,200 条内部链，最大长度 1,000，5/5 根因，无误报 |
| 所选 32 例耗时之和 | 7,679.08 秒，约 2 小时 8 分钟 |
| 含历史失败/复测的记录 | 39 次案例运行，6 次失败保留；耗时合计 8,990.70 秒，约 2 小时 30 分钟 |

耗时从本地启动器启动到退出计量，包含模型与 Scan 执行，不包含外部独立审计、案例生成和人工开发时间；不是整项开发的墙钟耗时或官方成绩。逐例实际镜像、轮次和耗时见 [成绩表](../benchmarks/scan32/scoreboard.md)。诊断自动评分采用真实脚本位置锚点，并逐项阅读了最终 29 个根因说明，确认与注入缺陷语义一致；不是官方评分算法。

## 文件位置与复现

生成器与独立验收：`dev/scan32.py`。生成资产位于被 Git 忽略的 `benchmarks/scan32/`：

- `inputs/Cxx_*/`：仅任务、限制、门级 Verilog、运行必需 Liberty；Task 2 附原始错误脚本。
- `oracles/Cxx_*/`：规模、预期分区、注入根因和参考脚本。模型运行不挂载此目录。
- `qualification/`：无模型的参考可行性运行，绝不计入模型通过率。
- `runs/<batch>/Cxx_*/`：真实 Luna 端到端运行，保留逐轮执行、失败、报告、产物与诊断证据。
- `manifest.json` 与 `README.md`：完整规模和能力矩阵。
- `scoreboard.md`：逐例成绩、耗时、执行轮次、根因指标与实际镜像；`results.json` 同时保留所选结果和所有批次尝试。

本地直接查看：[案例矩阵](../benchmarks/scan32/README.md)、[实测成绩](../benchmarks/scan32/scoreboard.md)、[完整机器可读结果](../benchmarks/scan32/results.json)。这些链接指向本机生成资产，Git 仓库不包含该目录。

```powershell
python -X utf8 dev/scan32.py prepare
python -X utf8 dev/scan32.py run --batch experiment01 --image localhost/scanscan:capability12
python -X utf8 dev/scan32.py score --batch experiment01
python -X utf8 dev/scan32.py report --batches experiment01
```

`prepare` 必须使用新目录；已有标准目录不要重复生成。`--folder` 可指定另一个新目录，`--cases C01_micro8 C25_deep_neutral_control` 可缩小运行/评分范围。每次运行输出目录必须是新的，不覆盖历史。

## 规模和难度

32 个原创参数化门级设计，8～1,200,000 个待扫描触发器（另加明确排除的寄存器）。每个普通数据位包含反馈 XOR，顶层数据端口保持有界，避免用百万端口制造模型上下文假压力。不是 32 个独立工业 IP。

能力轴：1～8 个时钟域/分区；同源时钟的独立层级分区；0～8 级门控；高/低有效复位；反相后的下降沿；模式选择与 MBIST 禁止条件；已有扫描 FF；显式长移位段；专用 Wrapper 和端口排除；合法不扫描寄存器；Task 2 多根因遮蔽，以及无故障阴性对照。

公开大例对照为 openC906 615,026、VeeR 799,031 个扫描单元。这里只有触发器数量可直接比较，不能据此宣称总体门数、功能多样性或工业复杂度超过公开 IP。

本地压力时限为 480 / 900 / 1800 秒，随规模递增；这是本地能力预算，不是官方时限成绩。大例顺序执行，避免在约 16 GB 的 Linux 虚拟机内并发百万级工具进程。

共 15 个 Task 1、17 个 Task 2，合计 6,631,660 个待扫描 FF；Task 2 包含 29 个注入根因和两个无故障对照。代表性的组合如下（这里描述题目，不把规模当成通过证明）：

| 案例 | 待扫描 FF | 关键挑战 |
|---|---:|---|
| C01_micro8 | 8 | 最小完整插链流程 |
| C25_deep_neutral_control | 768 | 8 级门控、复位、模式与链数，共 4 个根因 |
| C28_wrapper_repair | 4,096 | 专用 Wrapper 功能端口策略修复 |
| C29_clean_deep | 98,304 | 多域、层级、深门控组合中的无故障对照，不能凭复杂度臆造错误 |
| C30_falling_multi | 196,608 | 下降沿、多域、门控，3 个独立根因 |
| C31_hard_compound | 786,432 | 同源时钟的 8 个层级分区、8 级门控、复位和模式；另有 32 个必须保留的非扫描 FF |
| C32_extreme1m2 | 1,200,000 | 8 域、8 级门控；时钟、复位、门控极性、模式常量和链数共 5 个根因 |

C23、C24、C32 的扫描 FF 数量超过公开 VeeR 大例；其余包含微型、小型、中型和大规模设计。两例无故障对照为 C14 与 C29。

## 通过标准

真实 Scan 执行、正确的独立验收与逐字发布溯源是前提。额外核对：

- 每个分区的真实链数、逐链位数、源时钟和扫描使能；DRC 为零、复位/使能极性及模式常量。
- CTL 与报告逐链一致，原始寄存器完整且仅出现一次，不能靠少扫描、换分区或复制单元过关。
- 实际网表的 FF 类型、功能 D/Q/CLK/reset、SE、逐个扫描串行连接，以及原有反馈 XOR 网络。
- 层级端口及信号别名的等价连接；明确排除 FF 的类型与功能连接保持不变。
- 显式段注册及长度；Wrapper 端口策略和功能端点；物理可导出的 SCANDEF 链与 CTL 对应。
- Task 2 注入根因必须全部被定位，不接受额外假阳性；诊断锚点为脚本位置匹配，不是官方评分算法。

工具不为全由显式段组成的链输出 SCANDEF 条目；这不是漏链，CTL 和实际网表仍必须覆盖每一个原始 FF。实际边界由参考运行验证。

本验收不等于完整形式等价验证，也不能证明未见工业设计、隐藏题或官方分数。参考脚本不参与模型生成，也不作为运行时修复后备。

## 出题预检记录

最初生成器误用了 Verilog 保留字 `release` 作为内部端口名，参考工具在解析阶段拒绝。正式模型运行前改名为 `bypass`，电路与题目需求不变。原始失败输入和参考日志完整保留于 `benchmarks/scan32_preflight/`。

预检同时校正判分器对信号合并、层级端口映射、专用 Wrapper 重命名及纯段链 SCANDEF 导出的理解。判分没有降低功能、扫描覆盖或诊断要求。`dev/test_scan32.py` 以篡改串行线、篡改功能门和混入参考结果三个负例验证拒绝能力。

## 本轮已定位的系统问题

这些更改只使用任务文本、实际源码和工具报告，不读取 Scan32 的 oracle，不按案例名选择修复。

| 问题 | 共性修复 |
|---|---|
| 把分区选择器 ByClockEdge=both 当成实际边沿混合 | 保留有实际 ClockEdges 的单元报告样本，区分分区选择范围与观察到的单元边沿；修复回合保留原始证据以识别候选引入的新错误 |
| 把纯组合级联误当成需要逐拍初始化的锁存门控 | 说明状态传播与组合传播的区别；验证环节获得原始小型控制模块，不能仅凭修复后成功认定原始诊断成立 |
| 将高有效门控使能抽取成 constant=1 | 从明确 clock_gating 声明保留角色和用途，约束合并拒绝角色冲突；clock_gating 使能不被误套为所有 FF 链的扫描使能 |
| 将 Wrapper 链数和内部链数合并为一个全局数 | 数字抽取要求空 target，分区和 Wrapper 的已有独立解析保留各自作用范围；不静默接受错误 scope |
| 将 Wrapper 控制信号当成普通扫描控制 | 约束契约支持 wrapper_clock 与输入/输出 shift/capture 控制类型，逐角色核对实际报告 |
| 将要包裹的功能输出声明成 wrp_data_out | 明确 wrp_data_in/out 是串行测试通道，功能端口策略属于 set_wrapper_cfg；根据实际实现报告的 DFT Signal Port 原因定位错误 |
| 反复照抄工具示例中的 DRC Ignore | 将冻结的任务约束送入规划和修复；空 allowed_ignores 明确禁止所有降级命令，最终仍由独立执行验收把关 |

失败、重试和用过的镜像都保留。最终成绩表是指定批次按优先级合并的逐例结果，不能将跨版本修复后的全通过写成“同一冻结版本首次 32 连过”。评分动作只读取既有产物，不再次调用模型或 Scan。
