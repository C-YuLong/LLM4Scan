# 自建能力增强阶段（2026-10-01）

阶段结果：9 个自建案例累计有独立审计通过的产物；7 个注入根因全部正确识别，
两个无故障对照零误报。统一冻结的初始八例批次是 **7/8**，不是一次全过；
后续只复测受影响的失败/语义缺口。最新 capability6 只做纯文字案例定向验证，不能宣称该镜像全量通过。

## 范围与评分

本阶段新增初始 8 个自建任务及 1 个纯中文需求补充任务，覆盖多时钟、异步复位、组合门控三类小型门级设计。
包含 4 个故障修复任务（共 7 个注入根因）、2 个无故障对照和 3 个从零生成任务。
不是 9 个独立大型 IP；没有新增 Wrapper/CTL 黑盒、深层层级、大网表或 LEC 覆盖。
固定案例定义、评分和复现命令见 [cases/README.md](cases/README.md)。

产物按独立 oracle 全项通过计分，而不是只看 agent 的 accepted。除报告和 CTL，
还检查原始实例恰好覆盖一次、功能引脚、扫描使能及实际扫描串联连接。
诊断按根因计 TP/FP/FN，重复计算算 FP；无故障对照单独要求零误报。
这不是官方评分公式，目标为全部产物通过、故障诊断微平均 F1 ≥ 0.9、无故障对照零误报。

## 已实现的共性改进

1. **任务约束独立提取并冻结**：只向抽取调用提供任务文本，在生成/修复脚本之前建立
   带原文引用的数值、信号、配置和 Wrapper 约束。最终实现由模型选择任务行号、程序截取原文，
   不再让模型手工复制标点；极性显式区分 active_high/active_low 与 inactive_0/inactive_1，
   程序换算 off_state。复用原报告检查器；不让修复轮重写验收约束。
   已有确定性约束不能被模型放宽；冲突、无效值或虚构引用失败退出，保留抽取记录。
   尚未支持的语义在 `task_contract.json` 和验收的 unsupported 中显式保留。
   原文匹配只证明来源，不能证明模型语义解释正确，也没有穷尽所有遗漏。
2. **允许真实的零缺陷**：移除强制至少一个缺陷的输出/流程限制。
   当模型没有诊断出缺陷时，先核验 R1 的真实产物，满足程序和模型核验后直接发布；
   不为“做修复”而强制重写正确脚本。若原始产物不通过，仍进入修复，不能直接放行。
3. **诊断依据增强**：提供原始产物检查、小网表源码和报告，要求 violated_requirement
   是任务原文，不允许将建议的实现方式伪装成强制要求；保留被拒绝的模型条目。
   提示按最小语义修改归因：错误对象替换导致的下游缺失不是两个根因。
4. **测试答案隔离**：本地 runner 从挂载整个 dev/results 改成只挂载本例输出目录。
   最终验证实际检查了挂载：输入只读，输出独立，oracle 不可见；正式镜像不含开发案例。
5. 上一轮发现的分区表漏行修复继续包含在本阶段，不依赖案例名或分区后缀。

每次完整任务新增一次任务抽取调用；capability4 针对实际发生的契约失败最多纠错一次，
剩余时间不超过 30 秒时不尝试纠错。两次都受原有 wall-time 约束，不扩大时限。
无效候选、校验错误和 usage 保留，累计 token 包含失败的抽取尝试；不放松原文校验。
仍使用现有 Luna / Responses 路径；不是正式主办方接口适配。
OpenAI Docs 技能要求核对结构化输出文档，两处官方文档请求均 403；
本阶段沿用已有接口结构，并以实际服务响应验证新字段及零长度问题数组，不声称官方确认供应商别名。

## 探索过程与失败（不从成绩中隐藏）

- `capability_baseline01` 误选了尚未包含分区修复的 hardening2 镜像，首例遇到已知误拒，
  主动终止批次与对应容器。未完成，也不作为新的有效基线。
- `capability_dev01`：前三例因抽取结果不满足信号 target/value 契约失败，最后门控生成通过。
  前三例尚未保存原始抽取响应，不能进一步断言究竟哪个字段无效。随后保留抽取原文并明确
  “无端口名的全局描述不能生成空目标信号”。这是开发中的混合版本记录，不是统一镜像成绩。
- `capability_probe02_d_clock_count`：两根因准确识别与修复，产物通过，68.52 秒。
- `capability_dev02_d_reset`：复位极性修复通过，65.24 秒。
- `capability_dev02_d_clean`：正确返回零缺陷，但不必要的脚本重写包含路径声明而被拒绝。
  修复为核验原始结果后，`capability_clean03_d_clean` 在 R1 交付、零误报，55.61 秒。
- 首次留出：`capability_holdout_a01` / `capability_holdout_b01` 使用冻结 capability1，
  产物 4/4 通过，但无故障门控对照虚构“必须固定额外输入”的要求，1 个误报。
  两个故障案例 TP=4、FN=0；若把无故障误报一并计入，F1=8/9≈0.889，未达到阶段要求。
  前期 launcher 挂载范围仍较宽；模型输入未提供 oracle，但物理隔离尚不充分，不把它当强隔离证明。
- 门控误报被用于后续修复，因此最终对原 4 个留出案例的重测属于**已见回归**，不再称全新盲测。

## 验证边界

- 定向离线检查覆盖约束合并/冲突与原文引用、分区表两种形式、零缺陷核验和虚构要求拒绝。
- 对一份真实通过网表在临时副本中断开 SCD 连接，同时保持报告与 CTL 不变；
  独立评分器正确拒绝，说明产物评分不只是在重复检查报告。原始结果未被修改。
- 未重跑全部公开案例，未接入 SERV，未发布 GitHub 更新，未提交官方平台。
- 这组测试尚未覆盖高有效复位、锁存器、CTL 黑盒、专用 Wrapper、复杂层级和大例性能。
  必须继续保留真正未参与修复的独立设计，而不是把这组案例的通过记录解释为比赛满分。
